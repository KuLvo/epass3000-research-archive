# ePass3000 研究存档

存档日期：2026-11-20。状态：停止继续研究，保留实验代码与恢复说明；不作为生产级安全产品。

## 设备与研究结论

设备硬件 ID 为 VID_096E / PID_0401，BJCA 助手曾识别为 UKEY-G (FT3000)。旧证书为过期 RSA1024 证书；之后用户使用第三方 ePass3000 管理工具执行初始化及一键测试，原内容已被擦除并重新创建槽位 1 RSA2048 密钥。
历史实机测试证明当前槽位能完成 RSA2048 签名，独立 cryptography 验签及篡改拒绝通过；不等于完成硬件安全审计或证明所有导出路径均不可用。
卡片接口采用 libusb、R6 和 APDU，自定义 BER 公钥结构中的整数为小端。依赖与第三方管理工具相同的 WinUSB 访问方式。

## 已知限制

- 默认 PIN、PUK 和维护密钥未完成正式安全配置；硬件测试代码使用第三方工具的公开默认 PIN，仅适用于未修改的测试卡，勿在未知 PIN 状态下启用。
- 拔出 USB Key 不自动断开已建立会话。私钥不必离卡参与签名，但已认证的恶意主机仍可能请求签名。
- 公钥推送默认 Unix/Linux ~/.ssh/authorized_keys，要求服务器密码登录与 SFTP。拒绝符号链接；非事务式追加，尚未验证中断与并发写入情形。
- 删除配置只删除本地记录，不撤销远端公钥。没有做撤销授权或服务器策略更改。
- 终端自动测试不等于全终端兼容认证；未完成异常网络、所有 Windows 终端及长时间使用验证。
- 未打包独立 EXE；需要 Python、依赖库及本地 libusb DLL。SDK、第三方二进制许可未审查，不随源码存档分发。

## 恢复研究

阅读 README 安装依赖，按需从原管理工具取得匹配架构的 libusb-1.0.dll。运行 python -m unittest -v；只有确认设备及测试 PIN 适用才设置 EPASS_HARDWARE_TEST=1。
下一步优先验证 SDK PKCS#11 与原生 OpenSSH 兼容性，不兼容时再考虑 agent，避免继续扩大自制终端范围。
